# 005: Owner Received Form API

## Status

Done

## Goal

Continue the guest URL flow from spec 004. After a guest successfully submits the form, Quinten receives a Discord webhook notification and can retrieve the saved submission through the owner-authorized API, including downloading it as a vCard 3.0.

## Scope

- Send the configured Discord webhook a fixed `@everyone` notification after a successful guest submission, using the durable notification outbox and retry behavior established by spec 004.
- Add an owner-authorized endpoint to list retained guest submissions using privacy-minimizing summary fields.
- Add an owner-authorized endpoint to retrieve the contact details for one submission.
- Add an owner-authorized endpoint to generate and download one submission as a vCard 3.0 from its D1 record.
- Add focused API tests and local `.http` examples for owner retrieval and vCard download.

## Out of Scope

- Guest submission, link resolution, link consumption, or retention-policy changes specified in 004.
- Owner or guest interface changes.
- Manually deleting submissions, changing the 48-hour retention period, or adding search and filtering.
- Sending guest contact details or other user-provided content to Discord.
- Multiple owners, guest accounts, or unrelated account and management features.

## API Contract

All owner endpoints require `Authorization: Bearer <admin-token>`, following the existing owner API convention. Return `Cache-Control: no-store` on success and error responses. Never log the authorization header, guest contact values, or webhook URL.

### `GET /api/owner/submissions`

- Returns retained guest submissions ordered newest first.
- Returns a JSON object with a `submissions` array. Each item contains only `id`, `name`, `createdAt`, and `expiresAt`; do not include email, address, birthday, link identifiers, or credentials in this list response.
- Returns an empty array when there are no retained submissions.
- Does not return submissions whose `expires_at` is at or before the current time, even if scheduled cleanup has not removed them yet.

### `GET /api/owner/submissions/{id}`

- Returns the stored `id`, `name`, `email`, `address`, `birthday`, `createdAt`, and `expiresAt` for one retained submission.
- Returns `404` with a stable error code when the submission does not exist or is expired. Do not distinguish these cases.
- Does not expose its associated guest-link token, token hash, or other credentials.

### `GET /api/owner/submissions/{id}/vcard`

- Generates a vCard 3.0 from the retained submission record at request time; do not store a duplicate rendered guest vCard.
- Returns it as an attachment with `Content-Type: text/vcard; version=3.0; charset=utf-8` and a stable `.vcf` filename.
- Returns the same `404` behavior as the detail endpoint for missing or expired submissions.

### Authorization and errors

- Return `401` for missing or invalid owner authorization.
- Return `500` with a generic safe error for unexpected failures.
- JSON errors use the existing stable shape: `{ "error": { "code": "...", "message": "..." } }`.
- Responses must not contain internal exception details, secrets, or contact details beyond the fields explicitly returned by the authorized detail endpoint.

## Discord Notification

- Deliver notifications to the configured Discord webhook URL stored as a Cloudflare Worker Secret. Continue using the existing `WEBHOOK_URL` binding unless deployment configuration is deliberately revised.
- For each successfully persisted guest submission, deliver the fixed message `@everyone A new contact was submitted through ContactSwap.`
- The message is generated by the Worker and must not contain any guest-submitted values, submission identifiers, or other personal information.
- Include the Discord payload field `"allowed_mentions": { "parse": ["everyone"] }` so the fixed `@everyone` text triggers the requested notification. The webhook must have permission to mention `@everyone` in its target channel. Keep the message constant and never interpolate user-controlled text into it.
- Keep the existing outbox semantics: notification delivery is asynchronous and retried after delivery failures; webhook failure does not undo a successful submission or change the guest's success response.
- Do not log the webhook URL, request body, or response body. Do not include guest details in delivery errors.

## Data and Behavior

- D1 remains the canonical source for guest submission fields. Generate owner responses and guest vCards from the stored record, not from client-provided data.
- Only the owner-authorized API may return submitted contact details. Guest endpoints must not gain a way to read a submission after it is created.
- Expired submissions are unavailable immediately at the 48-hour `expires_at` boundary and are removed by the existing scheduled cleanup.
- Do not add stored fields or duplicate contact data unless required by these endpoints.
- Use the existing vCard renderer and output conventions. Escape contact values correctly and do not reveal a record when rendering fails.

## Acceptance Criteria

- Unauthorized requests to all three owner submission endpoints return `401` without disclosing submission data.
- The list endpoint returns retained records newest first with only the documented summary fields; it returns an empty list when no retained records exist.
- The detail endpoint returns the requested record's contact fields and timestamps only to an authorized owner. Unknown and expired IDs receive the same `404` response.
- The vCard endpoint generates a valid vCard 3.0 attachment from the requested database record with the documented content type, stable filename, and `Cache-Control: no-store`.
- Missing and expired records cannot be retrieved or downloaded, including during the interval before scheduled cleanup runs.
- A successful guest submission results in the exact configured Discord message being queued and eventually delivered. Delivery failures are retried without storing or sending guest contact details.
- The Discord payload permits the intended `@everyone` notification and contains no guest-provided data; the webhook's target channel allows that mention.
- Error responses do not reveal contact values, credentials, webhook configuration, or internal exception details.
- Automated tests cover authorization, empty and populated lists, list ordering and field minimization, detail retrieval, missing and expired IDs, vCard contents and headers, Discord payload/mention behavior, and webhook retry behavior using local Workers bindings only.
- Local `.http` requests demonstrate listing, retrieving, and downloading submissions without committed credentials or real personal data.
- Type checking, the API test suite, and production builds pass.
